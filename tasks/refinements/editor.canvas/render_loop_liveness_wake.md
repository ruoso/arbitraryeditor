## What this task is

**Arch A5** (`docs/01-architecture.md:227-233`) and the A4 data-flow it builds on make the canvas an off-thread renderer that publishes frames to the UI thread; the UI and the headless e2e/TSan lane observe rendering progress *only* through `published_sequence(id)`. **A4.1b** (`docs/01-architecture.md:189-225`) settles that external-load arrivals reach an install through three idempotent paths, one of which is *"the render thread's per-frame report"* — which silently assumes the render loop is still iterating when the arrival lands.

A nested raster resolves across **two distinct async stages** (confirmed against the fetched libarbc, `arbc/runtime/pending_external_loads.*`, `arbc/runtime/host_viewport.cpp:259-266`):

1. **External byte arrival.** The parent loads without the child; the deferring `AssetSource` fetches the child's bytes on its own thread and calls `PendingExternalLoads::complete()` — which **silently** stashes the bytes and bumps a counter (**no `poke`, no condvar notify, no callback**). The host learns of the arrival only when its *next* `step()` reports `StepOutcome::external_loads_ready > 0`, which it turns into one deduped async settle (`nudge_settle`, `canvas_host.cpp:419-420,151-170`); the settle's completion calls `wake()` (`canvas_host.cpp:166`). Until that first observing `step()`, nothing is in `pending().tiles` and `schedule_follow_up` is `false`.
2. **Raster tile pixels.** Once installed, the child's tiles flow through the normal worker-miss path and appear in `pending().tiles`, keeping `step()` truthy (the D-blank_first_frame-3 correction) so the loop drives until they reap.

The lost-wakeup is entirely in **stage 1**. First `step()`: the load is *requested* but not yet arrived — `external_loads_ready() == 0`, `schedule_follow_up == false`, `pending().tiles` empty. So `drive_once` returns `false`, `run` does not re-arm `dirty`, and the loop parks on the unconditional `cv.wait` (`canvas_host.cpp:469-470`). The bytes then arrive **silently** — there is no wake seam anywhere in libarbc to fire (worker-pool completion is an internal broadcast condvar that only wakes a thread already parked inside `wait_completions`, which the render loop is not; the external-load `complete()` is silent). The loop sleeps through the arrival forever; `published_sequence` never leaves 0 (the ~30 s stall the `D-writer_thread-10` anchor deadline, `canvas_host_test.cpp:1283-1286`, would hit absent its pokes).

This leaf restores liveness with a **poll-based resolving-vs-empty distinction**, since libarbc offers no async-completion wake to hook (see Decisions D-1). Concretely:

- **`drive_once` reports a second per-cycle signal: *external work is resolving*.** For each entry it already visits, `resolving |= entry->document->pending_external_loads() > 0 || entry->renderer.external_loads_ready() > 0`. `pending_external_loads() > 0` is the load-bearing term — it is true across the whole request→arrival window, the exact window the loop must stay alive through; `external_loads_ready() > 0` is a harmless belt-and-suspenders term (the nudge already wakes on it). A **genuinely empty document has both zero**, which is what distinguishes *resolving* from *empty* and keeps the fix from busy-looping an empty document (the constraint the `.tji` note names).
- **`run` splits the wait.** While the last cycle was *resolving*, park on `cv.wait_for(k_resolve_poll_interval, pred)` — a bounded re-poll that re-drives, witnesses `external_loads_ready() > 0` on the first cycle after the bytes land, fires `nudge_settle`, and lets the existing settle→`wake()`→re-render→composite→publish chain take over. While **not** resolving, park on the unchanged unconditional `cv.wait(pred)` — indefinite sleep, zero wakeups, so a genuinely idle canvas is byte-for-byte the same behavior as today (A4.1b / `editor.canvas.magnified_raster_idle`'s zero-wakeup idle discipline).

This is the render-side application of A4.1b's *"armed only while a fetch is outstanding"* rule — the same shape as the writer's `set_idle_work` poll, using the same witness (`pending_external_loads()`).

## Why it needs to be done

The published sequence is the editor's one cross-thread *"is the canvas showing the scene?"* signal, and the headless ASan/TSan lane depends on it advancing. Today it can stall forever whenever a nested-raster document's bytes happen to land on a render loop that has already gone cold — a rare, timing-dependent flake (surfaced once in 27 runs of the `group_transform` ASan/TSan anchor) that is nonetheless a genuine liveness bug: a user opening a project with a deferred-load nested raster could see a permanently blank canvas. The existing `D-writer_thread-10` "LIVE render loop" anchor does not catch it because it **pokes the host inside its pump loops** (`canvas_host_test.cpp:1273-1276,1283-1285`) — an artificial wake that production never sends after a silent arrival. A4.1b already promises the writer stays armed while a fetch is outstanding; this leaf makes the render loop honor the same contract, closing the gap A4.1b's *"render thread's per-frame report"* path silently assumed away.

## Constraints / requirements

1. **A genuinely empty / settled document sleeps indefinitely — zero wakeups.** When no entry is resolving (`pending_external_loads() == 0` and `external_loads_ready() == 0` everywhere) and nothing is pending, `run` parks on the unchanged unconditional `cv.wait`. No timer, no busy-spin — byte-identical to today's idle behavior (A4.1b idle discipline; the `magnified_raster_idle` invariant). This is the guard the `.tji` note demands ("a naive keep-spinning-while-`!content_published` busy-loops genuinely-empty documents").
2. **A silent external arrival can never land on a cold loop.** While any entry is resolving, `run` parks on a **bounded** `cv.wait_for(k_resolve_poll_interval, …)`, so within one poll interval of the bytes landing a `step()` observes `external_loads_ready() > 0`, `nudge_settle` fires, and the settle→`wake()`→composite→publish chain advances `published_sequence` — **without any external poke**.
3. **Bounded poll, not a spin.** The armed state re-polls on a fixed interval (a bounded `wait_for`), not an immediate `dirty` re-arm; the render thread does not burn a core while waiting on async bytes. A never-arriving load keeps the loop armed at the poll cadence indefinitely — the same benign steady state as the writer's `pending_external_loads()`-armed idle poll (A4.1b); it is an `AssetSource` fault, not idle, so bounded polling is the correct armed behavior. No total deadline is imposed (dropping a legitimately-slow load would be wrong).
4. **The *resolving* witness is exactly the two external-load poll accessors.** `pending_external_loads() > 0 || external_loads_ready() > 0`, read per entry from the render thread — both any-thread/lock-free (A4.1b `:211-214`; `shell.cpp:345` precedent). No new libarbc call, no worker-pool in-flight gauge (which libarbc does not expose live), no new state.
4a. **The worker-tile phase is untouched.** Stage-2 liveness stays on `step()`'s `!pending().tiles.empty()` term (the D-blank_first_frame-3 correction, `canvas_renderer.cpp:290`) via the existing `more_pending` immediate re-arm; the loop never sleeps while tiles are pending, so no worker-completion wake is needed. This leaf adds liveness **only** to the external-load window.
5. **Byte-exact pixels unchanged.** The fix changes *when* the loop re-drives, never what it composites; every existing byte-exact golden (`canvas_view_64x64.rgba8`, the `canvas_host` goldens, the deferred-nested byte-exact case `canvas_host_test.cpp:1093-1129`) passes **unmodified**.
6. **Render-thread-confined; no new cross-thread state (A4).** The witness is a render-thread poll of any-thread-safe accessors; `wake()`/`nudge_settle`/the double-buffer publish are untouched. No new lock, thread, channel, or shared field.
7. **Levelization (§8).** The change is confined to L2 `render` (`canvas_host.cpp`), reading two arbc `Document` accessors already used in the tree. **No new component, no new DAG edge, no ImGui/GL/SDL include** (`arbc/runtime/document.hpp` is already reachable via the existing `render → libarbc` edge; add the include if not already transitively present — that is not a new edge). `scripts/check_levels.py` stays clean.

## Decisions

**D-render_loop_liveness_wake-1 — The fix is a poll-based resolving-vs-empty liveness distinction, because libarbc exposes no async-completion wake the editor can hook.** The `.tji` note offers two shapes; the first (an async worker→render-loop completion wake) is **not achievable editor-side against the current libarbc API**, verified this task: worker-pool tile completion is an internal broadcast condvar (`WorkerPool::poke`/`wait_completions`, `worker_pool.hpp:200,212`) that wakes only a thread already parked inside `wait_completions` and does not survive `step()` returning; and external-load arrival (`PendingExternalLoads::complete()`, `pending_external_loads.cpp:75-82`) is entirely silent — no `poke`, no notify, no callback registration anywhere. Both async stages expose **only poll witnesses** (`pending().tiles`, `pending_external_loads()`/`external_loads_ready()`). *Rationale:* (i) with no wake to hook, the loop must keep *observing* the poll witness through the resolving window — which means it must not park indefinitely while a fetch is outstanding; (ii) the exact resolving window with no existing liveness is stage 1, the external-load request→arrival gap (stage 2 already keeps the loop hot via `!pending().tiles.empty()` + the `more_pending` immediate re-arm, the D-blank_first_frame-3 correction), so the witness is precisely `pending_external_loads() > 0 || external_loads_ready() > 0`; (iii) this reuses two any-thread accessors already in the tree (`shell.cpp:345`), adds no state, no thread, no libarbc change, and keeps the empty-document no-busy-spin guard by construction (empty ⇒ both witnesses zero ⇒ indefinite `cv.wait`). *Alternative rejected — an editor-side async completion wake:* park a dedicated thread in `renderer.worker_pool().wait_completions(...)` to `poke()` the loop. It reaches into the renderer's private park substrate, and — decisively — it would **not** cover the external-load arrival at all (whose `complete()` never pokes the pool), so it fixes the wrong stage. *Alternative rejected — keep spinning while `!content_published`:* the naive shape the `.tji` note explicitly warns against — it busy-loops a genuinely-empty document forever, violating the A4.1b/`magnified_raster_idle` zero-wakeup idle discipline. **Doc delta: D-2 (A4.1b amendment).**

**D-render_loop_liveness_wake-2 — The render loop applies A4.1b's *"armed only while a fetch is outstanding"* rule; record it as an in-place A4.1b amendment.** `run` parks on a bounded `cv.wait_for(k_resolve_poll_interval, …)` while the last cycle was resolving and on the unchanged unconditional `cv.wait` otherwise — the exact armed/disarmed shape A4.1b already prescribes for the writer's proactive settle poll (`docs/01-architecture.md:219-224`; `shell.cpp:339-346`), using the same witness (`pending_external_loads()`). *Rationale:* (i) it is not a new mechanism but the render-side twin of a decided one — same rule, same witness, same zero-wakeup-when-idle property, so a maintainer reading A4.1b should see both sides of it; (ii) A4.1b's current text names *"the render thread's per-frame report"* as one of three idempotent install paths but silently assumes the loop is iterating — this leaf makes that assumption explicit and correct, so the honest place to record it is *in* A4.1b, not a new row (the change refines a decided behavior rather than introducing a new decision, so the same-commit amendment rule applies, `tasks/refinements/README.md:85-91`); (iii) recording it protects the fix from a future "optimize the timer away" regression back to the unconditional wait that reintroduces the stall. *Alternative rejected — treat A4.1b as already fully governing and add no delta* (the `magnified_raster_idle` precedent, which asserted A4.1b/A5 unchanged): that leaf was a *test-only* assertion of a libarbc fix; this leaf changes the render loop's own wait discipline in `src/`, a behavioral fact A4.1b's writer-centric text does not currently state — leaving it unrecorded is the gap D-2 closes. *Alternative rejected — a whole new `A<n>` row:* overweight for what is a one-clause extension of an existing row; a new row would fragment the idle-discipline decision across two places.

**D-render_loop_liveness_wake-3 — Read the witness from `entry->document` inside `drive_once`; widen its return, add no `CanvasRenderer` accessor.** The per-entry loop already holds `entry->document` (it captures it for `nudge_settle`, `canvas_host.cpp:159`) and already calls `entry->renderer.external_loads_ready()` at `:419`, so `entry->document->pending_external_loads()` is co-located with existing external-load code; `drive_once` returns both `more_pending` and `resolving` (a two-field result / out-param — the implementer's call), and `run` consumes them. *Rationale:* (i) fewest new surfaces — no new public accessor threaded L2→L4, echoing `magnified_raster_idle` D-2's rejection of a new render/app observable added purely for a liveness signal; (ii) `pending_external_loads()` is the live `Document` truth, not the stale last-`step()` value the renderer caches, so reading it directly is also *more* correct than a renderer passthrough. *Alternative rejected — add `CanvasRenderer::pending_external_loads()` beside `external_loads_ready()`:* symmetric but an extra accessor for a value the host can read directly from the document it already holds; no added correctness. **No doc delta.**
