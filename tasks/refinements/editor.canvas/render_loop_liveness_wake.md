## Effort estimate

**1 day** (from the `.tji`). The change is small and confined to **L2 `render`** — the render-loop wait discipline in one file, plus tests:

1. `CanvasHost::run` (`src/render/canvas_host.cpp:494-519`) stops **busy-spinning** while tiles are in flight. Today, when `drive_once` returns `more_pending == true` it re-arms `dirty` and re-drives with no wait (`:510-517`), a genuine CPU spin whose only liveness guarantee is that `!pending().tiles.empty()` keeps flickering true. The loop instead **parks on the shared pool's completion substrate** — `impl_->pool.wait_completions(cursor, until)` (`worker_pool.hpp:212-213`) — seeded from `impl_->pool.settle_generation()` (`worker_pool.hpp:220`) so a worker's `poke()` on tile completion re-drives it, and a completion that raced in before the park returns immediately (the generation already advanced past the cursor).
2. `CanvasHost::Impl::wake()` (`src/render/canvas_host.cpp:141-147`) additionally calls `impl_->pool.poke()` (`worker_pool.hpp:200`) so a host event (add / resize / camera / scope / stop / the external-load settle poke) interrupts a loop parked in `wait_completions`, not only a loop parked on the host `cv`.
3. Tests: a deterministic L2 regression that pins the fix's mechanism via the already-exposed `CanvasHost::iterations()` liveness counter (`canvas_host.hpp:185`) — under the real bounded pool the loop must reach the first content frame in a **bounded** number of drive iterations (park-and-wake), where the pre-fix spin burns hundreds-to-thousands; plus a no-poke real-pool liveness assertion on the ASan/TSan lane.

No new render path, no new component, no new thread, no new channel, no new UI seam, no libarbc change, no pin bump. `WorkerPool::wait_completions`/`poke`/`settle_generation` are the park/wake substrate libarbc ships **for exactly this** (`interactive.hpp:352-355`: *"Exposed so externally-async content can `poke()` a render thread parked in this loop's `wait_completions`"*); the host already owns the `WorkerPool` (`canvas_host.cpp:87`) and already reads its own `iterations()` counter.

**Where the budget does NOT go.** Not the withhold gate (`content_published`, `frame_has_content`) — unchanged. Not `step()`'s `!pending().tiles.empty()` term (`canvas_renderer.cpp:334`) — it stays a valid "more work" hint; the fix changes only the loop's **wait**, not what a step reports or composites. Not the external-load (stage-1) path — out of scope (see Decisions D-3).

## What this task is

**A5** (`docs/01-architecture.md:227-240`) makes a canvas *"one `HostViewport` + `InteractiveRenderer` over the shared `Document`; multiple canvases are multiple renderers sharing one `WorkerPool`."* The editor's realization of that — `CanvasHost` — runs an off-UI-thread loop (`run`, `canvas_host.cpp:494-519`) that drives every entry's `step()` and publishes settled frames; the UI and the headless e2e/TSan lane observe rendering progress *only* through `published_sequence(id)`.

A raster cell resolves its pixels through the pool's **worker-miss** path: `step()` renders a frame, dispatches tile misses into `InteractiveRenderer::pending().tiles` (`interactive.hpp:286`), workers fill them off-thread, and a later `step()` reaps them. libarbc's intended non-spin loop *"parks in `WorkerPool::wait_completions` between `submit`-ing misses and calling `poll_refinements`"* — a worker (or externally-async content) calls `WorkerPool::poke()` on completion, which bumps a settle generation and wakes the parked thread (`worker_pool.hpp:184-220`).

**The editor's loop does not park there.** It parks on `CanvasHost`'s own `cv` (`canvas_host.cpp:498-499`) and, while `more_pending` is true, re-arms `dirty` and re-drives with **no wait at all** (`:510-517`) — a CPU spin. Its only liveness guarantee through the blank phase is that `step()` keeps returning true because `!pending().tiles.empty()` keeps flickering true (the D-blank_first_frame-3 correction). That is the lost-wakeup:

1. `step()` renders the blank first frame, dispatches tile misses → `pending().tiles` non-empty → `step()` returns true → the loop spins.
2. On some iteration, `poll_refinements` reaps the last currently-visible tile: `pending().tiles` polls **empty** for an instant while a worker is still finalizing another tile (its completion not yet folded into the queue), and this step happens to owe no `schedule_follow_up`. `step()` returns **false**; `drive_once` returns `more_pending == false`; `run` does not re-arm `dirty`; the loop parks on the unconditional `cv.wait` (`canvas_host.cpp:498-499`).
3. The worker finishes and calls `WorkerPool::poke()` — which wakes a thread parked in `wait_completions`. **The render loop is not parked there** (it is on the host `cv`), so the wake is lost. `published_sequence` never leaves 0; the loop sleeps through the settled tile forever (the ~30 s stall a `pump_until` deadline hits, `canvas_host_test.cpp:163-172`).

This leaf closes the gap by **parking the loop on the pool's completion substrate** whenever it might have outstanding tile work, so the worker's `poke()` is exactly the wake that re-drives it — the note's first option ("an async worker→render-loop completion wake so the loop re-enters when tile work completes without spinning"). Concretely:

- **`run` waits on `pool.wait_completions(cursor, until)` instead of spinning.** Before parking, seed `cursor` from `pool.settle_generation()`. If a worker settled between the last `step()` and the park, the generation has already advanced past `cursor` and `wait_completions` returns immediately → re-drive. This is the crux: the wake condition is the settle **generation**, not the racy `pending().tiles` poll, so the momentary-false instant that stranded the old loop can no longer strand it. Spurious wakes on the shared pool are bounded (one per sibling settle); the loop re-tests and re-parks against the same cursor (`worker_pool.hpp:192-199`).
- **`Impl::wake()` also `pool.poke()`s.** So an add/resize/camera/scope/stop/settle-poke interrupts a `wait_completions` park, keeping every existing host-event wake (`canvas_host.cpp:234,243,252,261,270,280`; `nudge_settle` → `wake`, `:171`) live.
- **A genuinely-empty / settled document still sleeps with zero wakeups.** No workers are running, so no `poke()` fires; the park (indefinite `until`, or a modest safety cadence) blocks until a host event pokes it — byte-identical idle behavior to today (Constraint 1; the `magnified_raster_idle` zero-core-burn invariant).

## Why it needs to be done

`published_sequence` is the editor's one cross-thread *"is the canvas showing the scene?"* signal, and the headless ASan/TSan lane depends on it advancing. Today the loop's liveness through the tile-resolving blank phase is a **spin whose exit condition is a racy poll** — it works almost always precisely because it spins fast enough to re-observe the tile, but the moment `pending().tiles` polls empty while a worker is still settling, the loop goes cold and the worker's `poke()` — the wake libarbc emits for exactly this — is discarded, because the editor's loop never parks where that wake lands. The result is a rare, timing-dependent stall (surfaced once in 27 runs of the `group_transform` ASan/TSan anchor) that is nonetheless a genuine liveness bug: a user opening a project with a raster-heavy scene could see a permanently blank canvas. The fix also eliminates the CPU spin itself — a secondary win the `magnified_raster_idle` sibling's `settle()` budget currently has to defend against. The existing anchors mask the stall because they **poke the host** inside their pump loops (`host.poke()` / `apply_edit`-driven pokes); production sends no such poke after a silent worker completion, which is why the deterministic regression below must reach content with **no** poke.

## Constraints / requirements

1. **A genuinely empty / settled document sleeps indefinitely — zero wakeups.** When no worker is running and no host event is pending, `wait_completions` blocks with no `poke()` ever arriving — byte-identical to today's idle behavior (A5; the `magnified_raster_idle` no-core-burn invariant). This is the guard the `.tji` note demands ("a naive keep-spinning-while-`!content_published` busy-loops genuinely-empty documents"). The distinction between *resolving* and *empty* is now structural: a resolving document has workers that will `poke()`; an empty one has none — no editor-side "is content coming?" predicate is needed.
2. **A worker completion can never land on a cold loop.** Because the loop parks on the same substrate the worker `poke()`s, and seeds its cursor from `settle_generation()` **before** the final `pending()` check, a completion that races the park is caught by the generation, not missed by the poll. Within one wake of the last tile settling, a `step()` reaps it, composites, and advances `published_sequence` — **without any external poke**.
3. **No busy-spin.** While tiles resolve, the loop **blocks** in `wait_completions` (condition wait, not a fixed sleep, not an immediate `dirty` re-arm); the render thread does not burn a core. A `bool` `until` timeout, if used, is a defensive re-check cadence only, not the primary wake. This removes the CPU spin `magnified_raster_idle`'s `settle()` budget currently absorbs.
4. **Host events still wake the loop.** Every existing wake path — add/resize/camera/scope requests, `stop`, `remove`, and the `nudge_settle` settle completion (`canvas_host.cpp:171`) — must interrupt a `wait_completions` park. Achieved by `Impl::wake()` also `pool.poke()`-ing; `wake()` remains the single fan-out point (`:141-147`) so no call site changes.
5. **Byte-exact pixels unchanged.** The fix changes *when* the loop re-drives, never what it composites; the withhold gate, `frame_has_content`, `step()`, and `convert()` are untouched. Every existing byte-exact golden (`canvas_view_64x64.rgba8`, the `canvas_host` composite goldens, the deferred-nested byte-exact case) passes **unmodified**.
6. **Render-thread-confined; no new cross-thread state (A4).** The loop reads/parks on the host-owned pool it already owns; `wake()`/`nudge_settle`/the double-buffer publish are otherwise untouched. No new lock, thread, channel, or shared field; the `CompletionCursor` is a render-thread-local of `run()`.
7. **External-load (stage-1) path untouched.** `pending_external_loads()` is **not** read from the render thread (the re-deferral blocker); this leaf does not touch external-load liveness at all (D-3). The regression uses **direct-seeded** (non-nested, non-external) rasters, matching the flake and avoiding both the `pending_external_loads()` unsafety and the arbc v0.4.0 threaded-nested-render detach SIGSEGV (memory: *arbc nested-render worker detach race*).
8. **Levelization (§8).** Confined to L2 `render` (`canvas_host.cpp`), using `WorkerPool` methods on the pool the host already owns and already includes (`canvas_host.cpp:12`). **No new component, no new DAG edge, no ImGui/GL/SDL include.** `scripts/check_levels.py` stays clean.

## Decisions

**D-render_loop_liveness_wake-1 — The fix is the note's first option: an async worker→render-loop completion wake, by parking the loop on `WorkerPool::wait_completions`. It is a race-free render-thread operation, so the re-deferral's blocker does not apply.** The `.tji` note offers two shapes. The first (a worker completion wake) is **achievable and correct** against the current libarbc API, verified this task: `WorkerPool::poke`/`wait_completions`/`settle_generation` are libarbc's documented park/wake substrate, exposed on the very pool the host owns, and libarbc explicitly intends a host render loop to park there (`interactive.hpp:352-355`, `worker_pool.hpp:184-220`). The second (a resolving-vs-empty *poll* distinction) was the 2026-07-29 draft's path; it foundered because the only editor-visible "resolving" witness for the stage that actually flakes would have to be a render-thread read of writer/load-thread-only load state, a TSan data race (see Status). *Rationale:* (i) the observed flake is a **worker-tile** stall, not an external-load stall — the `group_transform` anchor seeds rasters directly (`add_cell`, `canvas_host_test.cpp:770-772`), so `pending_external_loads() == 0` and no external load exists; the tile stage is exactly the stage libarbc gives a wake for; (ii) parking on the settle **generation** (cursor seeded before the final `pending()` check) closes the lost-wakeup at its root — the wake condition is no longer the racy `pending().tiles` poll that stranded the old loop; (iii) it removes the CPU spin as a bonus, aligning with `magnified_raster_idle`'s no-core-burn discipline; (iv) it reads/parks on state the host already owns, adds no thread and no libarbc change, and preserves the empty-document zero-wakeup guard **by construction** (no workers ⇒ no `poke` ⇒ indefinite park). *Alternative rejected — the poll-based resolving distinction over `pending_external_loads()` (the 2026-07-29 draft):* it targets the wrong async stage and requires a render-thread read of writer/load-thread-only maps (`PendingExternalLoads::pending()`), which TSan flags as a data race against the writer's `settle_external_loads` and the load thread's `complete()`. *Alternative rejected — keep spinning while `!content_published`:* the naive shape the `.tji` note explicitly warns against — it busy-loops a genuinely-empty document forever, violating the A5 / `magnified_raster_idle` zero-core-burn idle discipline. **Doc delta: D-2 (new A28).**

**D-render_loop_liveness_wake-2 — Record the adoption of the `WorkerPool` completion substrate as a new A28 row, cross-linked from A5.** The render loop's wait discipline is currently **undocumented** in `docs/01-architecture.md` (no `published_sequence` / render-loop / wakeup language appears anywhere in the file); this leaf establishes a normative fact — *the off-thread render loop parks on the shared `WorkerPool`'s `wait_completions`/`poke` substrate, so tile completions wake it without a busy loop and without a lost-wakeup; a settled/empty document parks with zero wakeups* — that a maintainer must not "optimize away" back to a spin or an unconditional `cv.wait`. *Rationale:* (i) it is a **new** architectural decision (the loop adopts an upstream park/wake seam it did not use before), not a refinement of existing doc text, so a new row is the honest form rather than an in-place amendment of a row that says nothing on the subject (`tasks/refinements/README.md:80-96`); (ii) A5 is the natural cross-reference (it already establishes the shared `WorkerPool`), so a one-clause pointer there ties the render/multi-canvas section to the new row without fragmenting A5's own decision; (iii) recording it protects the fix from a regression that reintroduces the spin/stall. *Alternative rejected — amend A4.1b:* A4.1b is the writer-thread/external-load row; this leaf is about the render loop's tile-completion wait, a different thread and a different substrate — folding it into A4.1b would conflate the two async stages that the re-deferral already proved must be kept distinct. *Alternative rejected — no delta (the `magnified_raster_idle` precedent):* that leaf was a test-only assertion of a libarbc fix; this leaf changes the render loop's own wait discipline in `src/`, a behavioral fact no current row states.

**D-render_loop_liveness_wake-3 — Scope this leaf to the worker-tile (stage-2) wake; leave external-load (stage-1) liveness exactly as A4.1b ships it.** The external-load arrival window is already covered in production: the writer proactively polls `external_loads_ready()` and settles, and the idle-work pokes the canvas (`shell.cpp:342-350`, A4.1b `:219-224`). This leaf does not touch it, does not read `pending_external_loads()` from any non-writer thread, and does not change any settle path. *Rationale:* (i) the flake is a tile stall, not a load stall — fixing the tile stage resolves the surfaced defect with no external-load change; (ii) the external-load stage has no editor-side race-free "outstanding" witness for the render thread (the re-deferral's finding), so any render-loop change there would reintroduce the blocked design; (iii) keeping the two stages separate honors the boundary the re-deferral established and keeps the change minimal. *Alternative rejected — also harden the external-load stage here (host-owned proactive poll):* out of scope for the surfaced flake, larger blast radius (touches `shell.cpp` and the D-writer_thread-10 three-path story), and unnecessary — production external-load liveness is not the bug. If a future defect shows an external-load stall on a cold loop despite A4.1b, that is a separate leaf against the writer path, not this one. **No doc delta beyond D-2.**
